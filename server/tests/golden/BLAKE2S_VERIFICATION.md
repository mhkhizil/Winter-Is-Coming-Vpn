# BLAKE2s verification record

Scope: `server/src/crypto/blake2s.cpp` + `server/include/vpn/crypto/blake2s.hpp`
(unkeyed, keyed, streaming, variable output length, key-block placement).

Verifier: `server/tests/golden/verify_blake2s.py`.
Reproduce:

```
cd server/tests/golden
python verify_blake2s.py --no-build                 # Python models only (offline)
python verify_blake2s.py --cxx <path to zig.exe>    # + builds and runs the real C++
python verify_blake2s.py --cxx <zig.exe> --markdown work/blake2s_table.md
python refresh_verification_doc.py                  # re-splices the appendix below
```

Last run: Python 3.14.7, `zig c++` 0.16.0 (clang front end, libc++), Windows
x86-64, `-std=c++20 -O2 -Wall -Wextra`. Exit code 0.

## What is compared

Four implementations, only one of which is the code under test:

| Model | What it is | Why it is independent |
|---|---|---|
| `hashlib.blake2s` | CPython's bundled BLAKE2s (the RFC 7693 reference code) | not derived from this repository; the authority for every expected value |
| `PortBlake2s` | line-by-line port of `blake2s.cpp`, including its ring buffer, key-block placement and `t_` counter handling | reproduces the *implementation*, so a divergence isolates a C++ defect |
| `rfc_blake2s` | from-scratch RFC 7693 §3.2/3.3 implementation with an explicit block list | different code shape from both of the above |
| `drivers/blake2s_driver.cpp` | the shipped `blake2s.cpp`, driven by a case file generated by the script | the thing under test |

Nothing in this record is compared against the implementation under test:
expected values always come from `hashlib`.

Tooling note: PyNaCl **cannot** serve as a cross-check here. The wheel is
installed at `work/pynacl` and its hash API is BLAKE2b-only
(`blake2b`, `crypto_generichash`); libsodium ships no keyed BLAKE2s-128, and
there is no `openssl` binary on this machine — which is exactly why
`blake2s.cpp` exists (see the header comment in `blake2s.hpp`).

## Case matrix (560 cases)

* Inputs: empty, `"abc"`, 1, 63, 64, 65, 127, 128, 129 and 1000 bytes
  (`byte[i] = (i*31+7) & 0xFF`, the same pattern the unit test uses).
* Keyed variants: key lengths **1, 16 and 32** bytes (32 is RFC 7693's maximum
  for BLAKE2s) plus the unkeyed case.
* Output lengths: **16 and 32** bytes for the fixed matrix (1..32 in the
  randomised set).
* Streaming: every fixed case is digested one-shot *and* with chunked
  `update()` calls at split points 1, 7, 63, 64, 65, 127, 128, 129 and 999 —
  the splits that straddle the 64-byte block boundary, where buffering bugs live.
* Randomised: 200 further cases from a fixed seed (lengths 0..300, key lengths
  {0,1,16,32}, output lengths 1..32, random chunk sizes).

## Outcome

| what | result |
|---|---|
| `hashlib` vs line-by-line port of `blake2s.cpp` | **560 / 560 match** |
| `hashlib` vs independent RFC 7693 model | **560 / 560 match** |
| **`hashlib` vs the real C++** (`zig c++` 0.16.0) | **560 / 560 match** |
| digests hard-coded in `tests/unit/test_blake2s.cpp` | **15 / 15 correct** (2 RFC + 13 golden) |

Verdict: **`server/src/crypto/blake2s.cpp` is correct** for every input, key and
output shape WireGuard needs — including keyed mode, the keyed-empty-message
case where the key block *is* the final block, 16-byte MAC-sized outputs and
output lengths that are not 32. No digest defect was found.

## Hard-coded vectors in `server/tests/unit/test_blake2s.cpp`

`verify_blake2s.py` re-derives **every** digest literal in that file from
`hashlib`:

* the two RFC 7693 Appendix B vectors (`empty_input_rfc_vector`,
  `abc_rfc_vector`) — both correct;
* all 13 rows of the `kGolden` table, each re-derived from **its own**
  `(data_len, key_len, out_len)` and the file's documented byte patterns, so a
  row whose digest is right but whose parameters are quoted wrong also fails;
* a coverage check that fails if any digest literal in the file is not one of
  the values `hashlib` produced (so a vector added later cannot silently go
  unverified).

Result: **15 / 15 correct; no wrong vector was found in the test file.**

## Not verified here

* Behaviour under `-fsanitize=address/undefined` (no such runtime on this
  machine); finding C-3 in `VERIFICATION_REPORT.md` (a key longer than 64 bytes
  handed to the `Blake2s` constructor overflows `buf_`) was found by reading the
  code, not by a sanitizer.
* Side-channel behaviour: the compression function is data-independent by
  construction, but no timing measurements were taken.
